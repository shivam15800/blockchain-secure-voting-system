BSVS system architecture and threat model

STRIDE analysis across all seven attack surfaces. Click any component name to drill down.

Component Category Threat Severity Mitigation
Frontend S — Spoofing Attacker hosts a phishing site with identical UI to steal wallet signatures on a fraudulent contract address High Display deployed contract address prominently in UI; enforce HTTPS; prompt users to verify domain and contract address before signing any transaction
Frontend T — Tampering XSS injection modifies the candidateId in the DOM between user selection and MetaMask signature construction High Strict Content-Security-Policy header; no innerHTML with dynamic data; React's default escaping covers most XSS; audit all third-party packages in the build
Frontend I — Info disclosure Browser console logs or local storage inadvertently persist the voter's candidate selection before the transaction is mined Medium Never log vote-intent data; clear sensitive React state immediately after transaction broadcast; no persistence of pre-submission vote state
Frontend E — Privilege escalation Admin dashboard is gated only on a frontend role check — any wallet address can navigate to the admin route and attempt privileged actions High Frontend check is display-only; all admin contract functions must have require(msg.sender == admin) — the on-chain guard is the authoritative enforcement point
Auth module S — Spoofing Attacker submits fabricated or borrowed identity credentials to pass voter registration without being a legitimate voter Critical Cryptographic credential validation (HMAC or digital signature over student ID + wallet address); reject credentials not signed by the auth service's own key; bind credential to wallet address at issuance
Auth module T — Tampering MITM attacker intercepts credential submission and substitutes a different wallet address, registering their own address as a legitimate voter High Enforce HTTPS for all auth API calls; include the wallet address in the signed credential payload so substitution invalidates the signature
Auth module I — Info disclosure Voter PII (student IDs, allowlist) is exposed via a misconfigured auth service endpoint or storage bucket High Hash voter IDs before storage; encrypt the allowlist at rest; apply least-privilege access controls; do not log raw identity data in application logs
Auth module D — Denial of service Auth service crash or overload during the registration window blocks all new voter registrations Medium Health monitoring with alerting; decouple auth from voting — auth failure must not affect voters who are already registered on-chain
VoterRegistry E — Privilege escalation Any wallet address can call registerVoter() and add arbitrary addresses to the on-chain voter roll Critical require(msg.sender == admin, "Not admin") on every privileged function; include a negative-case test that asserts a non-admin call reverts
VoterRegistry S — Spoofing Attacker attempts replay of a captured registerVoter() calldata to register an address a second time Medium On-chain mapping(address => bool) deduplication prevents double registration; EVM nonce mechanism prevents literal transaction replay; low residual risk if admin key is not shared
Ballot.sol E — Privilege escalation Voter calls castVote() multiple times, inflating a candidate's count because there is no double-vote guard Critical mapping(address => bool) public hasVoted; require(!hasVoted[msg.sender], "Already voted"); set hasVoted[msg.sender] = true BEFORE any downstream logic (Checks-Effects-Interactions)
Ballot.sol T — Tampering Reentrancy attack exploits castVote() if it makes an external call before updating hasVoted state High Strictly follow Checks-Effects-Interactions; update all state before any external call; add OpenZeppelin ReentrancyGuard as an explicit second layer
Ballot.sol I — Info disclosure VoteCast event emits both voter address and candidateId, permanently destroying ballot secrecy — anyone can reconstruct who voted for whom from the public event log Critical Emit VoteCast(address voter) only — no candidateId in the event. Store the candidate mapping in contract state, not in events. Document ballot secrecy as a known architectural limitation of this capstone scope
Ballot.sol D — Denial of service Unbounded candidate array causes getResults() to iterate past the block gas limit, reverting and making results permanently unretrievable Medium Enforce a maximum candidate count at election creation; use pull-over-push for results — return by index (getResult(uint candidateId)) not as a full array
Admin key E — Privilege escalation Admin private key is compromised, allowing an attacker to register unlimited fraudulent voters, close elections early, or lock the contract Critical Separate deployer key (one-time use) from election admin key; use a hardware wallet or multi-sig (Gnosis Safe) for the admin address; rotate after every election; never store in .env on shared machines
Admin key R — Repudiation Admin denies performing a fraudulent registerVoter() — without an off-chain audit trail, attribution relies solely on on-chain data which may be ambiguous in a shared-key scenario Medium All admin actions emit events with block timestamp; keep an off-chain audit log of each admin session including transaction hash; admin key must be single-person, not shared
Blockchain T — Tampering 51% attack on the Ganache local network or a small private testnet allows an attacker to rewrite vote transaction history High (local) Ganache is local dev only — never demo on Ganache as if it were production; use Sepolia (public PoS testnet) for demos; document that production requires a sufficiently decentralised network
Blockchain I — Info disclosure Pending castVote() transactions are visible in the public mempool before mining, revealing vote intent and enabling front-running Medium Accept as a known limitation of public EVM chains; document in the threat register; commit-reveal scheme is the full mitigation but is out of capstone scope
CI/CD I — Info disclosure Deployer private key is stored in plaintext, echoed in CI logs, or accidentally committed to the repository Critical GitHub encrypted Secrets only; never echo $PRIVATE_KEY in workflow steps; add a secret-scanning pre-commit hook (gitleaks); rotate the deployer key after each deploy
CI/CD T — Tampering A compromised GitHub Actions workflow substitutes malicious contract bytecode during the deploy step — the wrong contract is deployed to the testnet Critical Pin all Action versions to commit SHA (not floating tags); verify deployed contract bytecode hash post-deploy against the compiled artifact; require PR review for any changes to workflow files
CI/CD E — Privilege escalation Unprotected main branch allows a direct push that triggers an unauthorised testnet deployment without code review High Branch protection on main: require PR + at least one approval, no force-push; add a manual approval gate environment in GitHub Actions before any deploy job executes
